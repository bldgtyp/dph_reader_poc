# 00_Context — the foundation layer

Everything durable we know about the systems DesignPH-PLUS sits between: designPH, SketchUp (as a
*host* and, since 2026-08-29, as a *file format read without it*), Pyodide, and the honeybee stack.
Produced across spike Phases 0–3 (2026-08-19), substantially extended by the
POC's **first real end-to-end export**, the **full five-model corpus sweep**, and POC-5's
**downstream-consumer checks** (ph-navigator, live — `HONEYBEE_STACK.md` §6.4) — all 2026-08-21,
which is where most of the sharp-edged detail now comes from. **The POC is closed; this layer is
the part of its research a future V-0 leans on hardest.** Written so later work does not rediscover
any of it.

**Evidence base as of 2026-08-21:** five real project models spanning designPH 2.1.15–2.2.29 and
SketchUp 22–26, captured live and reconciled against an offline scan of all 14 corpus files. 545
classified faces, 239 windows, 99 thermal bridges, 3 TFA zones, four assembly tiers, and designPH's
own U-/R-value calculator as ground truth for the arithmetic.

**Extended 2026-08-29 (HEADLESS):** the same five models plus eleven more — **16 files, designPH
1.0.30 → 2.4.0 BETA, SketchUp 8 → 26**, including a **146 MB** model and a **second thermal-bridge
project (`2536 Holmes`, 42 named edges)** — read again through the SketchUp C SDK with no SketchUp
installed. That both re-confirmed every read rule *independently of the Ruby API* and roughly
doubled the corpus the rules are checked against.

**If you read one file, read [`CONSTRAINTS.md`](CONSTRAINTS.md)** — start at its **§0**, which says
which of two routes each constraint belongs to, then §8.1, "what the first real export settled, and
what it opened".

> ⚠ **There are now two routes, and this layer covers both.** The **extension route** runs inside
> SketchUp (Ruby + Pyodide in an `HtmlDialog`) and carries almost all of the runtime constraints in
> `CONSTRAINTS.md`. The **headless C-SDK route** (proven 2026-08-29) is a plain CPython process with
> no SketchUp installed, and *none* of the Pyodide, Chromium, threading or bridge constraints apply
> to it — it has its own instead. ★ **Everything about reading designPH transfers unchanged between
> them, and has been verified byte-for-byte.** The designPH knowledge is route-independent; the
> runtime knowledge is not. `CONSTRAINTS.md` §0 is the map.

> **Reading a rule dated 2026-08-21?** It came from running the whole pipeline against real corpus
> models in SketchUp 2022, with the output checked in Rhino/Grasshopper and the arithmetic checked
> against designPH's own dialog and the PHPP. Those are *measurements*, not inferences — and a
> striking number of them **overturned a rule that had been inferred from a single sample**: the
> window unit table, the aperture rectangle, the `*ID`/`*Auto` exclusivity claim, the section
> percentages, and both live-vs-offline count invariants. Where a claim is still inferred, it says so.
>
> ⚠ **The pattern is consistent enough to plan around: n=1 evidence on this project has been wrong
> more often than it has been right.** Adelphi alone masked every one of the count-invariant bugs;
> one window "confirmed" a unit table that holds on 20 of 46; three percentages fitted a scale rule
> that was backwards. Before generalising, check the claim against the whole corpus — the baseline
> and all five captures exist precisely so that is cheap.

## ⚠ Some of this now lives in `phi-rules` as well

The durable designPH knowledge in `DESIGNPH*.md` and the `.ppp` format have been consolidated into
the BLDGTYP **`phi-rules`** corpus as a reference ruleset, `rulesets/designph-2x-r1/` — reachable
from any repo through the **`phi-rules` skill**. That is where a *tool* looks it up; these files stay
the DesignPH-PLUS investigation record.

| There | Here |
|---|---|
| `tool/D01`–`D08` — designPH as a data store, generalised | `DESIGNPH.md`, `DESIGNPH_DATA_MODEL.md`, `DESIGNPH_FILE_FORMATS.md` — the same facts plus this project's reasoning and dead ends |
| `ppp/D09`–`D12` — the `.ppp`, mapped onto PHPP's named ranges | `PPP_EXPORT.md` — the licence line, which is a **DesignPH-PLUS** decision |

**Keep them in sync in one direction:** when something durable about designPH is *learned*, it goes
to `phi-rules`; this repo cites it. Two facts already flowed the other way and are recorded in both —
the `tempZone` refinement (`DESIGNPH_DATA_MODEL.md` §5.3.1) and the `.ppp` finding
(`PPP_EXPORT.md` header).

```
  └───────────────────────────────────────────┘                     │

  │ SDK_RUNTIME.md       what the C API gives │                     │
  │ HEADLESS_VIABILITY.md what it costs/breaks│                     │
  └───────────────────────────────────────────┘                     │

                       CONSTRAINTS.md summarises all of it — its §0 says which route each rule is for
```

⚠ **The two routes produce the same document.** A capture taken through route B and one taken
through route A differ in four named fields and nothing else, and translate to canonically identical
HBJSON. That is measured, not assumed — `planning/02_headless-reader/RESULTS/HEADLESS-B_results.md`.
