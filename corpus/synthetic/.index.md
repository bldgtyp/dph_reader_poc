# corpus/synthetic — synthetic scratch model + inspector dumps

A tiny hand-made designPH test model and the BT Attribute Inspector dumps taken from it during
spike Phase 0/1 (2026-08-19). Kept because the corpus baseline includes them and because of what
they taught — which is mostly a warning.

⚠ **The warning is the point: a synthetic model is not evidence about real models.** This six-face,
auto-classified, never-hand-assigned model produced the confidently wrong `*ID`/`*Auto`
version-rename rule that would have read **zero** area groups off a live 2.2 project
(`00_Context/DESIGNPH_DATA_MODEL.md` §6). Use these files to exercise *mechanics* (can the reader
parse at all); never to generalise a schema rule. Generalisation runs against the whole corpus
baseline (`planning/01_sketchup-export/feasibility/RESULTS/PHASE-0_corpus-baseline.md`).

| File | What it is |
|---|---|
| `designph_test.skp` | The synthetic model — six faces, designPH-classified automatically, SketchUp 2022 save |
| `designph_test~.skp` | SketchUp's backup of the same (`~` suffix). Counted as a separate corpus file in the Phase 0 baseline — historical attribute state can differ from the live file |
| `designph_test__attributes_260819_*.json` | Three **BT Attribute Inspector** dumps (`{model, model_dictionaries, selection}`): model-level dictionaries (GeoReference, designPH tables) plus per-selection `DesignPH_dict` reads, taken 2026-08-19 while establishing what designPH stores where |

Safe to experiment on (unlike `corpus/adelphi/` — those are irreplaceable), but the
never-modify-a-corpus-file rule still applies to the two `.skp`s: they are baselined key-by-key in
`corpus_baseline.json`, and editing them silently invalidates every count derived from it. Copy
first, like everything else.
