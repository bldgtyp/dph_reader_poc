**Keep verbatim (the load-bearing shapes):**

- `TCPServer` on `127.0.0.1`, OS-assigned port, 32-hex path token, COOP/COEP headers, MIME table,
  directory-escape guard, shutdown with the dialog.
- **Worker thread does all blocking I/O; a `UI.start_timer` callback whose only job is `sleep`

- Python import order ending in `import honeybee_ph`.
- The 6-second "dialog asked for nothing" diagnostic and per-request logging — they are what make a
  blank dialog attributable without an Ed round-trip.

```
    vendor/                  # generated by tools/vendor_payload.py — gitignored
```

Ruby namespace `DphPlusPoc`, one menu item **`Extensions ▸ DesignPH-PLUS POC ▸ Export HBJSON…`**
(`UI.menu("Extensions")` — the same menu the spike registered as `"Plugins"`) plus a
**`Diagnostics`** submenu (§3). Gitignore `poc/ext/dph_plus_poc/vendor/`, `poc/dist/`,
`poc/py/.venv/`, and `poc/_private/` (real corpus extractions/outputs — client data) the same way
the spike tree does.

## 3. Menu and diagnostics

The spike's three menu items exist because each isolates a failure class. Keep that property:

| Item | Purpose |
|---|---|
| `Export HBJSON…` | The product path. POC-1 wires it to the stub collector → fixture translate → save-file dialog |
| `Diagnostics ▸ Server only (open in browser)` | Serves with no dialog — separates "socket works" from "HtmlDialog accepts it" |
| `Diagnostics ▸ Runtime self-test` | Boots Pyodide, imports the stack, `Room.from_box` round-trip, bridge echo — ends in the verdict banner |
| `Diagnostics ▸ Save extraction JSON` *(checkbox)* | When on, `Export HBJSON…` also writes `<name>.extraction.json` beside the outputs — POC-5's sweep depends on it |

**Verdict banner is a hard requirement** (Phase 3 Finding 41): every dialog session ends with
`PASSED`/`FAILED` + a per-check list, and any closing message box carries the verdict. A run nobody
can grade at a glance has not reported anything. **The self-test's verdict JSON carries the
measurements** — `boot_ms`, `import_ms`, `wheel_unpack_ms`, `rbz_bytes`, `installed_bytes` — so §6's
numbers are read off it, not reported as prose.

## 4. The bridge, generalised slightly

Phase 3's bridge was `startSpike(json)` / `sketchup.spike_result(json)`. POC needs the same shape
with room for more than one action:

```
Ruby → JS   dialog.execute_script("DphPlus.dispatch(#{JSON.generate({action:, payload:})})")
JS   → Ruby sketchup.on_result(JSON.stringify({action:, ok:, payload_or_error:}))
```

Rules unchanged: **JSON strings only**, no geometry echoed back, errors serialised into the result
(never a silent console-only failure). Log payload sizes at both ends.

### 4.1 The JS↔Python seam and translator packaging — owned here, once

Three phases meet at this seam; POC-1 fixes it so they cannot invent it three ways:

- **The Python entry point is `dph_translator.entry.translate_json(payload: str) -> str`** — JSON
  string in, JSON string out (`{hbjson, report, verdict}` serialised), no proxies. POC-3's typed
  `translate()` is what `translate_json` wraps; JS calls only `translate_json` via
  `pyodide.runPythonAsync`.
- **The translator ships as a zip built from `poc/py/dph_translator/`** by `tools/vendor_payload.py`
  and is unpacked into Pyodide's FS by the **same `zipfile` path as the 8 wheels**. POC-1 builds
  this step against a stub package (§5.4); POC-3 fills the real one — no packaging change needed at
  integration.
- **`tools/build_rbz.py` fails if the vendored translator zip is stale** relative to
  `poc/py/dph_translator/` (hash check) — the "tests passed on code the .rbz doesn't contain"
  failure mode, removed structurally.

## 5. Steps

1. Copy and rename per §1; `ruby -c` every file.
2. Extract `server.rb`; port `test_static_server.rb`; run it offline — status codes, MIME, COOP/COEP,
   token, escape guard all green.
3. Port `tools/`; run `vendor_payload.py` + `build_rbz.py`; confirm `.rbz` size ≈ **6.66 MB**
   (the micropip-free Phase 3 final — `00_Context/PYODIDE_RUNTIME.md` §1; the oft-quoted 8.07/6.87 MB
   figures include micropip and are not the target). Record the unpacked-install size too — both
   numbers, per the house lesson.
4. Wire the stub seam: the stub collector returns a checked-in minimal extraction JSON (authored in
   this phase; POC-3's synthetic set supersedes it), and the stub `translate_json` parses it, emits
   one `Room` from its `faces` records, and returns `{hbjson, report, verdict}` with an empty
   report — **the same signature POC-3 replaces** (§4.1).
5. Drive the built page in **headless Chromium 88** via `verify_in_chrome.py`: boot, unpack, imports,
   fixture round-trip, verdict JSON out. ⚠ The harness's `CHROME` default is the *modern* installed
   Chrome — a false green. Use the recorded snapshot (rev `827102`,
   `00_Context/SKETCHUP_RUNTIME.md` §4.2, from
   `commondatastorage.googleapis.com/chromium-browser-snapshots/Mac/827102/`) via `--chrome`, and
   assert the harness reports **major version 88** — anything else is not a verification. This is
   the agent's own gate — green before Ed is asked.
6. **[Ed]** One SketchUp session, runbook staged by the agent (pattern: `PHASE-3_ed-runbook.md`):
   install `.rbz`, run `Diagnostics ▸ Runtime self-test`, then `Export HBJSON…` on any open model
   (stub path), paste the verdict JSON back.

## 6. Gate

**PASS:** self-test verdict `PASSED` inside SketchUp 2022 (boot, imports, bridge echo, fixture
HBJSON written via the save dialog); Chromium 88 harness green; server tests green; cold start within
2× of Phase 3's 2.6 s.
**FAIL:** any silent hang (that means a threading rule was broken — diff against the spike, do not
debug forward); or boot regression past ~5 s (find what the restructure added).

Record in `RESULTS/POC-1_results.md`: measurements vs Phase 3's table, any deviation from the spike
architecture and why, and the `.rbz`/installed sizes.
