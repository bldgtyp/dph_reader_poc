# `pyodide/` — Phase 3 spike code

Does real, unmodified honeybee + honeybee-ph run inside SketchUp's `HtmlDialog` via Pyodide?
Findings: [`../../01_sketchup-export/feasibility/RESULTS/PHASE-3_results.md`](../../01_sketchup-export/feasibility/RESULTS/PHASE-3_results.md).
Ed's part: [`../../01_sketchup-export/feasibility/RESULTS/PHASE-3_ed-runbook.md`](../../01_sketchup-export/feasibility/RESULTS/PHASE-3_ed-runbook.md).

Throwaway spike code, kept regardless of outcome (`AGENTS.md`). Read-only against every model.

## The one idea worth knowing before reading any of it

`spike.js` and `spike.py` are **host-agnostic and shared verbatim** between the SketchUp extension,
the desktop-Chrome harness and a plain CPython run. Only the thin outer shells differ. That is what
makes a failure attributable: if a step passes in Chrome and fails in SketchUp, the difference is
`HtmlDialog`, because nothing else changed.

## Layout

```
vendor_payload.py     downloads + verifies the pinned runtime and wheels     → vendor/  (gitignored)
build_rbz.py          syntax-checks, trims, zips, optionally installs        → dist/    (gitignored)
verify_in_chrome.py   drives headless Chrome over CDP, 4 configurations      → ../../RESULTS/baselines/
probe_pyodide_syntax.py  which Pyodide releases a given Chromium can parse
test_static_server.rb the real static server, over a real socket, no SketchUp
ext/
  dph_plus_spike.rb           loader stub — the only file SketchUp auto-loads
  dph_plus_spike/
    main.rb                   HtmlDialog, the loopback static server, the face reader, the bridge probe
    html/index.html           host shell for HtmlDialog
    html/spike.js         ★   shared: Pyodide boot, wheel install, measurement, bridge probe
    html/spike.py         ★   shared: import the stack, build a model, round-trip it
    vendor/                   staged by build_rbz.py (gitignored)
harness/harness.html          host shell for desktop Chrome — same spike.js, same spike.py
```

## Running it

```bash
uv run planning/spikes/pyodide/vendor_payload.py            # ~8.5 MB of downloads, pinned + sha256
uv run planning/spikes/pyodide/verify_in_chrome.py          # all four Chrome configurations
uv run planning/spikes/pyodide/build_rbz.py --install       # build + copy into SketchUp 2022
ruby planning/spikes/pyodide/test_static_server.rb         # the Ruby half, offline
```

CPython control run — the same `spike.py`, for attributing a slow number to Pyodide or to honeybee:

```bash
uv venv .venv-hb && uv pip install --python .venv-hb/bin/python --no-deps \
  planning/spikes/pyodide/vendor/wheels/*.whl
.venv-hb/bin/python planning/spikes/pyodide/ext/dph_plus_spike/html/spike.py --faces 1441
```

`verify_in_chrome.py --mode` picks one configuration:

| mode | What it isolates |
|---|---|
| `file` | The realistic `HtmlDialog#set_file` origin situation. **Fails** — see Finding 20 |
| `file-permissive` | The same, with `--allow-file-access-from-files`. Passes — names the capability CEF would need |
| `http` | The loopback-server architecture. Passes |
| `extension` | The extension's *own* `index.html`, driven by a stub `sketchup` host. Exercises the bridge protocol without SketchUp |

## Testing against SketchUp's actual engine

`HtmlDialog` is **not** the Chrome on your machine. SketchUp 2022 embeds **Chromium 88** — read it
off `SketchUp.app/Contents/Frameworks/Chromium Embedded Framework.framework/Resources/Info.plist`.
A matching snapshot downloads and drives headlessly, which is how the Pyodide version ceiling was
found without a single SketchUp run:

```bash
curl -sL -o chrome88.zip \
  https://commondatastorage.googleapis.com/chromium-browser-snapshots/Mac/827102/chrome-mac.zip
unzip -q chrome88.zip
uv run planning/spikes/pyodide/verify_in_chrome.py --mode http \
  --chrome ./chrome-mac/Chromium.app/Contents/MacOS/Chromium --tag _c88
```

The driver picks `--headless` below Chrome 109 automatically.

## Two things that will bite

- **`micropip` is not shipped, and that is deliberate.** It is coupled to the Pyodide release and
  cannot run on the 0.24.1 that Chromium 88 forces. Every wheel is `py3-none-any`, so `spike.js`
  unpacks them with Python's `zipfile` — unpacking *is* installing. Phase 2 planned the reverse.
- **The vendored Pyodide is pinned at 0.24.1 by SketchUp 2022's Chromium 88**, not by preference.
  0.28+ will not parse, 0.25–0.27 will not instantiate their wasm. Raising the pin means raising the
  supported SketchUp floor — PRD §7.4.
- **`extension` mode serves the *staged* copy** in `ext/dph_plus_spike/vendor/`, not `vendor/`.
  Re-vendor without rebuilding and the two drift; the driver now refuses rather than reporting a
  stale runtime's failure as the new one's.
- **A Ruby `Thread` is starved in SketchUp and the socket still binds** — so the server is pumped by
  `UI.start_timer`, and the symptom of getting this wrong is silence rather than an error. This cost
  a round trip through Ed; `test_static_server.rb` cannot catch it, because plain Ruby threads work.
- **`Space.from_room` raises on a Room with no Floor face**, which is a perfectly normal designPH
  selection — only area groups 1 and 11 become floors. Reported, never raised (hard rule 4).
